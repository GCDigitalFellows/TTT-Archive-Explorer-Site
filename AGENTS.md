# Instructions for agents reviewing or revising this deployment

This repository contains the public website outputs for Tagging The Tower Archives Explorer. The canonical research source and full agent instructions are in the private [TTT-Archive-Explorer repository](https://github.com/GCDigitalFellows/TTT-Archive-Explorer/blob/main/AGENTS.md). Access may be required. Do not claim to have reviewed inaccessible source or run unavailable checks.

- Review assignments are read-only unless revision is explicitly authorized. Do not launch other agents unless expressly authorized for the current task. AI audience simulations are not human user studies.
- Before editing, packaging, and immediately before pushing, run `python3 scripts/check_shared_updates.py --public-checkout /path/to/public-site` from the private checkout. Review both working trees and fetched branches. Hold dependent work and publication if a comparison fails. If a new commit substantially conflicts with or changes the revision plan, show Ian the commit, impact, and proposed resolution and await approval. Preserve contributor edits and commits. Integrate routine compatible changes without asking; never force-push or discard others' work. Seek Ian G. Williams's approval before integrating significant changes to data, authorship, membership, methods, conclusions, architecture, substantial deletions, rights, privacy, access or deployment policy, unless that specific change is already approved. Show the concrete change, provenance, impact and proposed integration.
- This is a deployment repository. Prefer revisions in the source templates/builders followed by reviewed packaging. Preserve direct GitHub edits and carry them back into the source/template or packager when authorized, so regeneration does not undo them. If source access is unavailable, report that limit and the exact proposed patch; do not silently replace the site with a partial rebuild. Do not expose private source history, credentials or raw inputs.
- Every implemented update appears as one sentence in the README changelog. The full `CHANGELOG.md` records the date, concrete change, separate human and AI contributions, evidence and limits. Coordinate the matching source work log and README through the source maintainer. Source packaging normally synchronizes the changelog; do not silently erase entries from either repository. Git author attribution does not establish manual writing or absence of AI assistance.
- Preserve evidence boundaries: posting account versus article writer versus curator/source author; fellowship status at publication versus guest/GCDRI participation; signed semester snapshots versus directory intervals versus undated current roles. Missing membership evidence does not prove nonmembership. Keep drafts, full archive, local posts, modeled posts and selected essay examples distinct, with honest denominators.
- Keep keyword signals, interpretive themes and MALLET topics distinct. Browser filters reuse saved outputs; they do not fit a new model. Avoid changing frozen evidence or authorship/identity mappings without documented support and the required authorization.
- Write code and explanations for human reviewers with limited technical experience. Review handoffs should identify revision/scope, findings and severity, source passages or file/record references, proposed or actual edits, checks actually run, uncertainty, required decisions and attribution notes. Do not claim human approval or validation merely because an AI review or automated check passed.

Ian directs this project; original post writers retain separate source authorship. Newly created code/analysis licenses remain for Ian to specify. Existing public/private boundaries remain in force.

## Human review and teaching

This website and its code are a pedagogical tool. Future changes must support reviewers who are learning to understand and edit the code and design in VS Code. Read the source repository’s `docs/CODE_REVIEW.md` and pedagogical instructions when access is available.

- Use explicit steps, descriptive names, focused functions, and the pinned source formatting. Explain purpose, inputs, outputs, assumptions, and non-obvious decisions in plain language.
- Identify editable source files and settings for copy, styles, layout, charts, and analysis parameters. Explain their effects, required dependencies, generated outputs, rebuild command, and a focused check. Maintain the source code map and VS Code tasks when those routes change.
- Use small, clearly labeled examples when they help a learner. State what a command writes. Preserve source quotations, research evidence, attribution, keyboard behavior, responsive layout, and accessibility safeguards while demonstrating an edit.
- Label source changes, model fitting, and publication steps and follow their existing approval rules. Record actual checks separately from assumptions about learner understanding. If private source is unavailable, identify the missing context and the maintainer’s required source change.

## Required CRediT and GAIDeT attribution

- Apply both frameworks to every implemented task, with separate attribution. CRediT describes supported human contributions; GAIDeT describes tasks delegated to generative AI. Neither framework establishes human authorship eligibility, approval or a one-to-one mapping between human roles and AI tasks.
- Use the canonical roles and saved GAIDeT category/task IDs in [the published contribution profile](credits/process_profile.json), with its framework citations and version/access limitations. Do not invent labels/IDs or claim a fresh taxonomy audit. Assign humans only the work they actually contributed; requests, supplied sources and specific corrections do not establish personal execution or verification of all code/data. AI agents receive no human CRediT role. Original post authors retain source-text credit separately.
- For each AI tool/agent, record known identity/model label, inspected revision/input, performed task, output, checks and uncertainty. Mark unknown provenance explicitly. Separate external reviews, agent synthesis and implementation; distinguish generative-AI assistance from NLTK/MALLET/script computation. Record actual human oversight and contributor confirmation; simulations and automated tests are not human review.
- Coordinate the matching source work-log fields (`human`, `agent`, `credit_roles`, `gaidet`, `evidence`, `limit`) and project/scoped disclosures with the source maintainer. The public README and full changelog must reflect the same human/AI attribution. Preserve historical statements as historical; do not backdate later verification. If source access is unavailable, supply the proposed attribution and evidence as a handoff and state that synchronization is pending.
- For examples from the saved taxonomy: Code generation `0000017`, Validation `0000023`, Text generation `0000030`, Proofreading and editing `0000031`, Summarizing text `0000032`, Quality assessment `0000044`, Identification of limitations `0000046`, Recommendations `0000047`. Choose by actual work, not by convenience; do not label all drafting as summarization or claim unperformed checks.
- When source checks are available, run the relevant `analysis/credits` and `analysis/process` tests and inspect the substantive attribution. Report only checks actually performed. Published profile access does not imply access to the private source or contributor confirmation. See the [contribution disclosure](CREDITS_AND_PROCESS.html) and [work log](WORK_LOG.html).
